# PLAN Template Guide

This is a template and guide for writing effective initiative PLAN.example.md files.

## Required sections

### Tasks
**What this section should contain:**
- Specific, actionable implementation tasks
- Each task should be completable in 1-4 hours
- Use checkboxes for completion tracking
- Include testing/validation tasks
- Include documentation tasks

**Template:**
- [ ] [Specific implementation task 1]
- [ ] [Specific implementation task 2] 
- [ ] [Specific implementation task 3]
- [ ] [Testing/validation task]
- [ ] [Documentation task]

### Decisions
**What this section should contain:**
- Key technical and product decisions made during implementation  
- The reasoning behind each decision
- Record decisions as they're made (don't wait until the end)

**Template:**
[Record key technical and product decisions made during implementation]
- [Decision topic]: [Decision made and reasoning]

### Risks
**What this section should contain:**
- Identified risks that could impact the initiative
- Mitigation strategies for each risk
- Update as new risks emerge

**Template:**
[Identified risks and mitigation strategies]
- [Risk description]: [Mitigation approach]
- [Risk description]: [Mitigation approach]

### Progress notes
**What this section should contain:**
- Regular updates on progress (daily/weekly)
- Blockers encountered and how they were resolved
- Timeline of what happened when
- Context for future readers

**Template:**
[Daily/weekly progress updates, blockers encountered, solutions found]

**Date format example:**
**Feb 6, 2026:** Completed template backbone creation
- [Specific accomplishment]
- [Blocker encountered and resolution]
- [Next steps identified]

### Done when
**What this section should contain:**
- Clear completion signals
- Should align with acceptance criteria from README
- Specific, verifiable completion indicators

**Template:**
[Clear completion criteria - when can we confidently say this initiative is finished]
- [Completion signal 1]
- [Completion signal 2]

## Best practices

**Task breakdown:**
- Break work into manageable chunks (1-4 hours each)
- Include non-coding tasks (research, documentation, testing)
- Use active verbs ("Create", "Implement", "Verify")
- Be specific enough that someone else could pick up the work

**Decision logging:**
- Record the decision AND the reasoning
- Capture alternatives considered
- Note any constraints that influenced the decision
- Record who made the decision if relevant

**Risk management:**
- Be proactive - identify risks early
- For each risk, define what you'll do about it
- Update risks as work progresses
- Don't just list risks - include mitigation plans

**Progress tracking:**
- Update regularly (don't wait until the end)
- Include dates for all updates
- Record what you learned, not just what you did
- Note blockers and how you resolved them

**Completion criteria:**
- Should be verifiable by someone else
- Must align with README acceptance criteria
- Include both functional and quality gates
- Be specific about what "done" means

## Common mistakes to avoid

**Tasks:**
- Tasks that are too large or vague
- Missing testing/validation tasks
- No documentation tasks
- Tasks that don't align with the initiative scope

**Decisions:**
- Recording decisions without reasoning
- Waiting until the end to document decisions
- Not updating decisions when they change
- Missing key architectural decisions

**Risks:**
- Only listing risks without mitigation plans
- Not updating risks as work progresses
- Missing obvious technical or process risks
- Being too optimistic about risk likelihood

**Progress notes:**
- Only updating at the very end
- Not including enough context
- Focusing only on what was done, not what was learned
- Missing important blockers or challenges faced
